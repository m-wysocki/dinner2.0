# 05.1: Email-confirmation hardening (code review follow-up)

**What to build:** Address the code-review findings on 05 so the confirm-email flow is correct, deduplicated, and specific to confirmation links.

**Blocked by:** 05: Email confirmation

**Status:** resolved

## Background

Follow-up from the code review of 05. The review found no hard violations, but flagged a few actionable items in the confirm-email implementation and its contracts:

- `/auth/confirm-email` accepts any valid confirmed access token — it never checks the link's `type=signup` fragment, so it also works for a normal login-session token (a "mark my app user confirmed" endpoint rather than a confirmation-link endpoint).
- `emailConfirmedAt` is recorded as `new Date()` (server processing time) instead of the Supabase-reported `email_confirmed_at`, so the stored timestamp can differ from the actual confirmation time.
- `registerResponseSchema` and `confirmEmailResponseSchema` are field-for-field identical; the Prisma-row → response `*.parse(...)` mapping is duplicated in `register` and `confirmEmail`; the duplicated error-shape guard in `isRecordNotFound` mirrors `isEmailUniqueViolation`.
- `extractAccessToken` hand-rolls URL-fragment parsing; `dinner2://confirm` is centralized as `EMAIL_REDIRECT_TO` in the service but repeated across tests.

Deferred (out of scope for this ticket): reconciling a user who confirms the email by clicking the link in a browser rather than the deep link is covered by 08 (current-user) session handling; requiring Supabase's "Confirm email" setting is a dashboard configuration, not code.

## What to do

- On `/auth/confirm-email`, require the confirmation-link `type=signup` fragment (in addition to `access_token`); reject links that are not confirmation links with `INVALID_CONFIRMATION_LINK`.
- Record `emailConfirmedAt` from the Supabase user's `email_confirmed_at` timestamp instead of `new Date()`.
- Introduce one shared user-response schema used by both `register` and `confirm-email`, and a single private mapper from the Prisma user row to that schema, removing the duplicated schema and mapping in `auth.service.ts`.
- Reuse the existing error-shape guard for both unique-violation and record-not-found handling, and prefer `URLSearchParams` (or Supabase's callback-URL parsing) over hand-rolled fragment parsing.
- Keep the register/confirm mobile contracts and tests in sync with any shared-schema change.

## Definition of done

- [x] `/auth/confirm-email` rejects links whose `type` is not `signup`.
- [x] `emailConfirmedAt` reflects Supabase's `email_confirmed_at`.
- [x] The register and confirm-email responses share one schema, and the row→response mapping is defined once.
- [x] Confirm-email flow has tests covering the `type` check, the timestamp source, and the shared schema.
- [x] Workspace typecheck, lint, formatting, tests, and builds pass.

## Resolution

`/auth/confirm-email` now requires the `type=signup` fragment alongside `access_token` and rejects anything else with `INVALID_CONFIRMATION_LINK`. `emailConfirmedAt` is recorded from the Supabase user's `email_confirmed_at`. `register` and `confirm-email` share one `authUserResponseSchema` and a single private `toAuthUserResponse` mapper. The two Prisma error-shape guards were merged into one `isPrismaError(error, code)`, and the deep-link fragment is parsed with `URL` + `URLSearchParams` instead of hand-rolled parsing. Mobile contracts and tests were kept in sync with the shared-schema rename. Tests cover the `type` check (service + e2e), the timestamp source, and the shared schema. Typecheck, lint, formatting, tests, and builds all pass.
